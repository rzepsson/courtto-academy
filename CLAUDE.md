# CLAUDE.md

Guidance for AI agents and developers working in this repo. Keep it accurate — update it when an architectural decision changes.

## What this is

**courtto academy** — multi-tenant B2B SaaS for tennis & padel schools. Each school is a tenant, modeled as a Better Auth **organization**.

**Stack:** Nuxt 4 · Nuxt UI 4 (Tailwind v4) · Drizzle ORM (PostgreSQL, postgres-js) · Better Auth (`organization` plugin) · @nuxtjs/i18n (en/pl) · motion-v (animations). Package manager: **pnpm**.

## Product vision & future architecture

Two products are planned on **one shared backend + database**:

- **Courtto Academy** (this app) — B2B SaaS for managing racket-sport **schools**. Every user here is a **tenant member** (belongs to a specific org): owner/admin run the school, coaches teach, students have their own in-tenant panel (`/my`). This is *not* a public marketplace — a student is a member of one school, not an anonymous consumer.
- **Courtto** (future, separate) — a public court-**booking marketplace** ("Booksy for courts"): players discover and book courts. Different audience, SEO/public traffic, mostly anonymous/light accounts, different scaling & branding.

**The split is consumer-vs-admin, not product-vs-product.** Planned shape (industry-standard: Booksy + Booksy Biz, Playtomic + Playtomic Manager):

- **Consumer Courtto = its own app** (separate frontend/deploy/domain) — a public marketplace shouldn't share a frontend with an authed dashboard.
- **Admin/provider panel = one shared app** (this one grows). An org is a `school`, a `facility`, or **both**; areas are **capability-gated** by the org's `types` (see the type/status model discussed for `orgProfile`: `types[]` capabilities, org-wide `active`/`suspended` status, and per-facility verification — orthogonal axes, never one enum). A single owner running a school *and* renting courts logs into one panel.
- **Shared core** = DB, `server/services`, `shared/permissions`, schema, auth, org/members/notifications/settings. This is the most valuable asset and what makes the expansion cheap.

**Active soft rule until then (no restructuring now — build Academy to completion first):** keep the generic core product-neutral. `org`, `members`, `roles`, `notifications`, `auth`, `settings/profile` are shared plumbing — do **not** weave Academy-specific concepts (lessons, coaches, students-as-domain) into them. Academy-domain logic lives in its own services/areas on top of that core. Then extracting the core to `packages/core` (pnpm workspaces) when Courtto starts is moving files, not rewriting. **Flag it** when Academy-specifics start leaking into the generic core.

## Layout (Nuxt 4)

`srcDir` is `app/` — pages, components, composables, layouts, `app.config.ts`, `app.vue` live there. Auth screens use `layouts/auth.vue` (a single centered column: brand mark above the form card, locale/theme switch top-right, no side panel). Login/register pages use a subtle staggered `MotionReveal` entrance on their content (title, form, footer link) for a more polished feel — kept short (`y="8"`, ~0.08s stagger) so it doesn't read as sluggish. **Page/layout transitions are disabled** (`app.pageTransition: false` in `nuxt.config.ts`): `mode: 'out-in'` drops the incoming page's content whenever the target has async `setup` (Suspense), which every dashboard page does, so client-side nav rendered a blank panel until refresh. The app shell is `layouts/dashboard.vue` (Nuxt UI `UDashboardGroup` sidebar + user menu). Brand assets: `components/AppLogo.vue` (SVG mark) and `components/BrandMark.vue` (lockup, `horizontal` prop for the sidebar). The Nitro `server/` dir is at the **project root**.

```
app/            pages, components, composables, app.config.ts, app.vue, assets/css
server/
  api/          HTTP handlers — thin, call services only
  utils/        auto-imported: db.ts, auth.ts, org.ts, session.ts, services/*
  database/     schema.ts (generated), app-schema.ts (hand-written app tables),
                types.ts (hand-written)
shared/         permissions.ts — org roles + access control, imported by BOTH
                server/utils/auth.ts and app/utils/auth-client.ts
i18n/locales/   en.json, pl.json
```

## Non-negotiable rules

1. **Services pattern.** All Drizzle queries live in `server/utils/services/*`. API handlers in `server/api/*` only call services — never import `db` or write queries in a handler.
2. **DB & auth are plain module-level singletons** (no factories, no `useRuntimeConfig`): `export const db` / `export const auth`, reading env via `import { env } from 'node:process'`. Better Auth auto-reads `BETTER_AUTH_SECRET` / `BETTER_AUTH_URL` from env — don't pass them in config.
3. **`server/database/schema.ts` is GENERATED — do not hand-edit it.** Run `pnpm auth:generate` (the `auth` CLI + an eslint --fix pass). It emits the auth/org tables with FK indexes, `$onUpdate`, and drizzle `relations()`. Hand-written convenience types go in `server/database/types.ts`. **App-owned tables** (not Better Auth's) go in `server/database/app-schema.ts` — that file survives regeneration; both are merged in `db.ts` (`{ ...schema, ...appSchema }`) and both are listed in `drizzle.config.ts`.
4. **Better Auth owns its tables.** `organization` etc. have `id`/`createdAt` as notNull with no DB default — Better Auth populates them. So services over these tables are **read-only**; create/update/delete go through Better Auth's API (e.g. `auth.api.addMember` for programmatic membership), never a direct Drizzle insert. This rule is scoped to Better-Auth-owned tables; services write to **app-owned** tables (`app-schema.ts`, e.g. `orgJoinCode`) with Drizzle directly.
5. **i18n — no hardcoded UI text.** Use `const { t } = useI18n()`; messages in `i18n/locales/*.json` (strategy `no_prefix`). Brand wordmark ("Courtto" / "Academy") in `app/components/BrandMark.vue` is the one deliberate exception. **Error messages are localized too** — never surface a raw `error.message` from Better Auth or a server response to the user (it's untranslated English). Failures carry a stable code (`error.code`, or `data.code` on a Nitro `createError`); the `useApiError()` composable (`resolve`/`toastError`) maps it to `error.codes.<CODE>` in the locale files, falling back to generic localized copy for unknown codes / rate limits / network errors. The key-selection policy is the pure, unit-tested `resolveErrorKey`/`normalizeError` in `app/utils/errors.ts`. Codes come from Better Auth's `BASE_ERROR_CODES` (core) and `ORGANIZATION_ERROR_CODES` (org plugin) — e.g. a taken slug is `ORGANIZATION_ALREADY_EXISTS` (create) / `ORGANIZATION_SLUG_ALREADY_TAKEN` (update), **not** `SLUG_IS_TAKEN`.
6. **Nuxt UI theming.** Brand color is vibrant neon/emerald green: `ui.colors.primary: 'green'` in `app/app.config.ts` + the `--color-green-*` ramp in `app/assets/css/main.css`. Don't restyle Nuxt UI components with inline Tailwind at the call site — change `app.config.ts` instead.
7. **Comments are minimal.** This repo may go public. Don't comment self-evident code; comment only genuinely non-obvious decisions.

## Conventions

- **Env vars (plain, no `NUXT_` prefix):** `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`. `drizzle.config.ts` reads `process.env.DATABASE_URL`. **Object storage (optional)** for logo uploads: `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET`, `S3_PUBLIC_URL`, `S3_FORCE_PATH_STYLE` — read lazily in `server/utils/storage.ts` (S3-compatible: R2/S3/MinIO). Unset → uploads return 503 and the settings UI degrades; nothing else breaks. **Transactional email (optional):** `SMTP_HOST`, `SMTP_PORT` (default 587), `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SECURE` (`true` → TLS/465, else STARTTLS), `MAIL_FROM` (the From header) — read lazily in `server/utils/mailer.ts`. Unset `SMTP_HOST`/`MAIL_FROM` → the **loud console transport** (prints every mail, link included, to the server log — never a silent no-op; see the mail layer below). **Observability (optional):** `OBSERVABILITY_WEBHOOK_URL` — read lazily in `server/utils/monitoring.ts`; when set, every incident is POSTed as JSON (in addition to the always-on structured console log); unset → structured console only (see the observability layer below). **Billing (optional):** `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_STARTER`, `STRIPE_PRICE_PRO` — read lazily in `server/utils/billing-config.ts`; unset → every school runs on the 14-day app-managed trial and the pricing UI degrades to a "not configured" notice (see the billing layer below).
- **Drizzle adapter:** the built-in `better-auth/adapters/drizzle` (version-matched to core), not the standalone `@better-auth/drizzle-adapter`.
- **Performance:** `experimental: { joins: true }` is enabled in `auth.ts` (2–3× faster `get-session`/`get-full-organization`); it relies on `import * as schema` (with relations) being passed to both `drizzle()` and `drizzleAdapter()`.
- **Animations:** `motion-v` via the `motion-v/nuxt` module (`Motion`, `MotionConfig`, … are auto-registered). A global `<MotionConfig reduced-motion="user">` wraps the app in `app.vue`, so all motion honors the OS reduced-motion setting. Two tiers:
  - **Micro-interactions everywhere** — press/hover springs on buttons (`components/PressButton.vue`), hover lifts on cards/tiles.
  - **Entrance animations** via `components/MotionReveal.vue` (fade + rise; `delay` prop staggers siblings) — used on dashboard (client area) content, and, subtly (`y="8"`, ~0.08s stagger between sections), on the login/register forms (`app/pages/login.vue`, `register.vue`) for a more polished first impression. No page/layout transitions (disabled in `nuxt.config.ts`); use `<NuxtLoadingIndicator>` (in `app.vue`) for route-change feedback and `MotionReveal` for content.
  - **Loading:** data-heavy pages fetch with `useLazyFetch` and render `USkeleton`/`components/AppListSkeleton.vue` while `status === 'pending'`, so navigation is instant and content streams in.
- **Fonts:** `@nuxt/fonts` self-hosts Public Sans, picked up from `--font-sans` in `app/assets/css/main.css`. `html` has `scrollbar-gutter: stable` so appearing/disappearing scrollbars don't shift the layout.
- **Client data fetching:** components/composables use `useFetch`/`useAsyncData` against internal `/api/*` routes — never call the server layer directly (e.g. `app/composables/useOrganizations.ts`).

## Auth & sessions

- **Client actions:** one Better Auth client singleton in `app/utils/auth-client.ts` (`createAuthClient` from `better-auth/vue`, same-origin — no `baseURL`). Sign in/up/out call `authClient.*` directly from pages.
- **Reading the session:** `app/composables/useAuthSession.ts` exposes `useAuthSession()` = `useFetch('/api/session')` (SSR-safe, cookies auto-forwarded) and `refreshAuthSession()`. `/api/session` (`server/api/session.get.ts`) returns `{ session }` (nullable inside — a bare `null` body would become an empty response and trigger useFetch's undefined-value warning); the composable unwraps it via `transform`. This is the single source of session truth — don't read sessions any other way on the client.
  - **Do NOT use `authClient.useSession(useFetch)`** — it passes a `{ ref }` option Nuxt's `useFetch` ignores, so the cache never invalidates after sign-in/out (stale session → broken redirects).
  - **After every auth transition** (`signIn`/`signUp`/`signOut`) call `await refreshAuthSession()` **before** `navigateTo`, or middleware reads the stale cached session. Also call `clearAppContext()` (from `useAppContext`) on these transitions — the `app:context` cache is keyed globally, not per-user, so without clearing it the previous user's memberships/roles leak into the next session in the same tab.
- **Route protection:** named middleware `app/middleware/auth.ts` (require session → `/login`) and `guest.ts` (redirect authed → `/dashboard`), applied per-page via `definePageMeta({ middleware: ... })`.
- **Server-side route protection:** `server/utils/session.ts` exports `getUserSession(event)` (nullable) and `requireUserSession(event)` (throws 401). Custom API handlers needing auth call `requireUserSession` first (template: `server/api/me.get.ts`).
- **Email verification is OFF** — sign-up logs the user straight in. This is a deliberate product decision (kept even though a mail provider now exists — see the mail layer): turning it on changes the signup flow and is a product call, not a side effect of adding email.
- **DB migrations:** schema changes (re-run `pnpm auth:generate` when auth tables change) are applied via `pnpm db:generate` (emit SQL to `server/database/migrations/`) then `pnpm db:migrate`. Use migrations, not `db:push`.

## Account & self-service data rights

`/account` (`app/pages/account.vue`, reached from the sidebar user menu) — what a person may do with their own login, independent of any school: name, email, password, signed-in devices, a copy of their data, and closing the account. **CORE, product-neutral** — it moves with the core when Courtto is extracted. It carries **only the `auth` middleware, no area guard**, so it stays reachable for a suspended membership or a school whose subscription lapsed: both of those are states of a *school*, not of an account (same reasoning as `/access-paused` and `/billing-required`).

- **Better Auth owns every mutation** (rule 4): `updateUser` (name), `changeEmail`, `changePassword`, `listSessions`/`revokeSession`/`revokeOtherSessions`, `deleteUser` — all through `authClient.*`, enabled in the `user` block of `auth.ts`. The app adds only the two things Better Auth can't know: the deletion guards and the export.
- **`changeEmail` runs with `updateEmailWithoutVerification`.** Email verification is off by product decision, so `emailVerified` is always false — which is the only branch the change-email route can take without a verification mailer. Turning verification on later makes the option inert rather than wrong, so it needn't be revisited in the same change. The route answers **200 without applying the change when the address already belongs to someone** (enumeration safety by design); the card therefore re-reads the session after saving, so a rejected change visibly snaps back instead of looking like it worked.
- **A password change always `revokeOtherSessions`** — it is how someone reacts to a suspected compromise, so it must actually evict, not merely re-key. Better Auth re-issues the caller's own token, so the current device stays signed in.
- **Deletion is guarded, and ORDER IS THE SAFETY PROPERTY.** `beforeDelete` → `services/account.ts`: (1) `findAccountDeletionBlocker` refuses to strand a school — `ACCOUNT_OWNS_SCHOOL` when the user is the **only** owner of any org (`member.userId` cascades, so deleting the sole owner leaves a school nobody can administer; same lockout reasoning as the ownership-transfer and owner-status guards, and the same fix: transfer ownership or delete the school). It's returned, not thrown, so the rule is testable without catching and the Better Auth boundary owns the error shape. (2) `prepareAccountDeletion` **stops billing BEFORE the delete**, because `member` → `enrollment` → `enrollmentBilling` all cascade and that last row holds the Stripe subscription id — exactly the `purgeSeries` rule; skipping it charges a family monthly for a spot that no longer exists, with no record anywhere. Both steps are best-effort, so a Stripe outage never traps someone in an account they want closed; the residual risk deliberately runs the recoverable way (billing stopped for a delete that then failed → staff resends a link, and the money-audit trail shows it). Each school the person belonged to gets a **`member.account_deleted`** audit entry written before the cascade — the FK-free, name-snapshotted columns are what let a roster still explain the member who vanished.
- **The export (`GET /api/account/export`, JSON download)** is scoped by the session's user id, with no id parameter to tamper with: account, every membership, guardians, consents, enrolments, attendance, notifications. Set-based (one query per record type across all memberships, grouped in memory), so it doesn't fan out per school. **Staff-only CRM fields are deliberately excluded** (`memberProfile.notes`/`tags`, guardian and consent `notes`): the codebase treats them as never visible to the member, and — the deciding reason — for a school's records about its students **the school is the controller and Courtto the processor**, so a full art. 15 request belongs with the school, which can weigh third-party rights and exemptions. The page says exactly that in plain language rather than implying the download is the whole picture. The controller-side export/erasure is a separate surface (see the gaps list).
- **Verification:** unit (`test/unit/account.test.ts` — user-agent parsing, the form schemas) + server (`test/server/account-service.test.ts` — the guard's per-school rule incl. the co-owned/stranded mix, the per-org audit fan-out, export scoping + tenant isolation + CRM omission, **and the Better Auth wiring driven through `auth.api.*`**: the sole-owner refusal with its code, a real deletion cascading the membership while the trail survives, a wrong password, the direct email change, the session eviction). That last block is the only coverage of the `user` config — a typo'd option would otherwise pass every static gate and fail only in the browser.

## Legal documents, terms & consents

The contract layer: the terms a school accepts, the privacy information Courtto owes its users, the DPA it owes them as a processor, and the one consent it collects for itself. **CORE, product-neutral** — the future Courtto marketplace needs the same acceptance trail, so nothing here mentions schools or lessons.

- **The documents live in `docs/legal/`, not in the code.** `pl/` is binding, `en/` is a courtesy translation (stated in the documents themselves). Four Polish documents: `regulamin.md` (uśude art. 8 terms, B2B — Courtto ↔ School), `polityka-prywatnosci.md` (art. 13/14 information duty + cookies), `umowa-powierzenia.md` (art. 28 DPA + three annexes: scope, sub-processors, TOMs), `wzory-zgod.md` (templates the **school** uses with its students — image/marketing consent + the art. 14 clause for guardians). `docs/legal/README.md` carries the versioning rule, the open decisions, and the proposed retention table. **They are drafts pending review by Polish counsel** — placeholders are in square brackets.
- **The rendered page reads the same bytes git versions.** `/terms` and `/privacy` import the Markdown with Vite `?raw` and render it through `app/utils/markdown.ts` — a small renderer for exactly the subset these documents use (headings, lists with indented sub-clauses, tables, blockquotes, checkbox items, inline forms). **Retyping the documents into Vue templates was rejected**: a terms page that has drifted from the accepted document is the one bug in this area that actually matters. The renderer HTML-escapes every span, so the single `v-html` in the app is fed build-time repo content that cannot contain live markup. `components/LegalDocument.vue` owns the reading typography (`layouts/legal.vue`, wide column).
- **Versions are one constant — `LEGAL_DOCUMENT_VERSIONS` in `shared/legal.ts`** (`RRRR-MM-DD`). It is what the page shows, what an acceptance records, and what `needsReacceptance` compares against. A unit test asserts the constant **matches the `**Wersja:**` line in the source document**, so a bumped file with a stale constant (or the reverse) fails the build rather than silently recording agreement to a wording never served. Bumping does NOT notify anyone — art. 8(3) uśude requires advance notice plus a right to terminate, a separate deliberate step.
- **Acceptance is recorded SERVER-SIDE, from `databaseHooks.user.create.after`** (`auth.ts` → `services/legal.ts` `recordLegalAcceptance`). The versions come from the server, never the client: a version the browser claims to have read is not evidence. Best-effort + `captureError` — a failed evidence write must never block someone creating an account, but it is never silent. `userAgreement` (`app-schema.ts`, migration **0025**) is **append-only, one row per acceptance event**: a re-acceptance after a bump inserts a new row and keeps the old one, because "agreed to THIS wording on THIS date" is the only question that matters later. `ipAddress`/`userAgent` are nullable — a programmatic sign-up has no request context.
- **The consent model mirrors `member-consent.ts` and is deliberately just `marketing`.** Running the service someone signed up for is performed on the basis of the **contract** (art. 6(1)(b)); a "consent to process my data" checkbox would be withdrawable at will (art. 7(3)), so honouring a withdrawal would mean shutting off a paid account mid-term. A unit test guards the omission. `userConsent` (unique on `(userId, type)`) holds current state: **withdrawal keeps the row and never clears `grantedAt`** — that timestamp is the art. 7(1) evidence of the period during which sending was lawful — and absence of a row is `asked: false`, which blocks sending just like a withdrawal but is a different job (never asked vs. a decision to respect). `mayContactForMarketing` is the only question the rest of the app should ask.
- **The registration checkbox is mandatory and the marketing one is separate, optional and unticked** — a consent bundled with a mandatory acceptance is not freely given, so it is not a consent. The marketing PUT runs after sign-up (it needs the session) and is best-effort: a failure stores no consent, and no consent means no marketing — the only safe failure direction. **REST:** `GET /api/legal/state`, `POST /api/legal/accept` (re-accept after a bump), `PUT /api/legal/consent/[type]`. All account-level (`requireUserSession`, no area guard), so they stay reachable for a suspended membership or a lapsed subscription — same reasoning as `/account`. `/account` gained a **Documents & consents** card (links, last acceptance, a re-accept prompt when outdated, one-click withdrawal that asks for nothing).
- **No cookie banner, and that is a deliberate asset.** Verified in the code: only the Better Auth session cookie (+ signed `cookieCache`) and `courtto_locale` — all strictly necessary or functional, so art. 398 PKE requires information, not consent. There is no analytics, no pixel, no external font (`@nuxt/fonts` self-hosts). **Adding Google Analytics, a Meta pixel, an embedded map or a CDN font immediately creates a consent obligation** (a real "reject" button, not just "ok") and invalidates section 8 of the privacy policy. Flag it if one is proposed.
- **Business continuity is contracted for, and it is only as real as the export it rests on.** § 16 of the terms (ust. 7–15, mirrored in the DPA § 10 ust. 6–9) commits to 90 days' notice before shutting the Service down, read+export access throughout, a pro-rata refund, and — the clause worth having — that **Organization data is never an asset of Courtto**, so it cannot be sold, pledged or disposed of in a bankruptcy separately from the agreement, and confidentiality binds a trustee or liquidator too. It also states honestly that a trustee's statutory power to withdraw from unperformed mutual contracts can outrank a contractual promise, which is why the school is told to take its own regular export. **That last part currently overclaims: there is no Organization export** — only `/api/account/export` (the account holder) and the members CSV. Recorded as the BLOCKING item at the top of `docs/legal/README.md`; `exportAccountData` is the pattern to copy. Do not publish the documents before it is built or the clauses reworded.
- **Two further open items, both recorded in `docs/legal/README.md`:** (1) `memberProfile.notes` / `memberGuardian.notes` are free text that staff **will** fill with health data ("astma", "alergia") — art. 9 special category, a different regime. The documents handle it *contractually* (§ 11.4 of the terms + Annex 1 pt 4 of the DPA exclude it), which is lawful but stops nobody; the real fix is a separate `medicalNotes` field with its own basis and narrower access. (2) Retention is proposed per table but **not implemented** (gap #11), so the shipped policy states current behaviour ("until the account is deleted") rather than the target — keep the two in step when the sweep lands.
- **Verification:** unit (`test/unit/legal.test.ts` — version/source agreement, the `needsReacceptance` rules, the consent-type omission, fail-safe reads, and the renderer incl. HTML escaping, code-span isolation, and a pass over **all six shipped documents** asserting no raw markup leaks) + server (`test/server/legal-service.test.ts` — **that the Better Auth hook actually fires and records acceptance on a real sign-up**, append-only history, per-user scoping, and the consent lifecycle incl. `grantedAt` surviving withdrawal). That hook test is the one that matters: unwired, there is no evidence anyone ever agreed to anything, and no static gate would catch it.

## Organizations, roles & invitations

- **Roles** (per membership, single role): `owner`, `admin`, `coach`, `student` — defined once in `shared/permissions.ts` (`ac` + `roles`, wired into both the `organization()` plugin and `organizationClient()`). `INVITABLE_ROLES` excludes `owner`. Role labels/colors render via `app/components/RoleBadge.vue`. (A former `parent` role was merged into `student`; `toOrgRole()` coerces the legacy value, so no data migration was needed.)
- **Role-based routing:** `/dashboard` never renders — middleware `resolve-home` redirects to the active-org role's home: owner/admin → `/school`, coach → `/coach`, student → `/my`; no membership → `/onboarding`. The mapping lives in `roleHome()` (`app/utils/org.ts`). Area pages use middleware chains `['auth', 'school'|'coach'|'my-area']` built on `resolveAreaRedirect()` (`app/utils/area-guard.ts`).
- **Active organization:** `session.activeOrganizationId`, seeded by a `databaseHooks.session.create.before` hook (first membership) and switched via `authClient.organization.setActive` (see `useOrgSwitch()`). `GET /api/app-context` (composable `useAppContext()` / `refreshAppContext()`) returns memberships + a **validated** active org id — the single client source of org/role truth.
- **Server-side org guard:** `requireActiveMembership(event, allowedRoles?)` in `server/utils/org.ts` — custom `/api/school/*` handlers call it first.
- **Two ways to join a school:**
  - **Personal email invitations** — for staff (admin/coach) and any role-specific add. Owner/admin creates one via `authClient.organization.inviteMember` (7-day expiry); the recipient is **emailed** the invite (the org plugin's `sendInvitationEmail`, wired to the mail layer) **and** the modal still shows the copyable `/invite/[id]` link — the email is **additive**, the link is the fallback when mail bounces. The landing endpoint `GET /api/invitations/[id]` is public by design (the id is the unguessable token; the email is masked server-side). Accept/reject go through `authClient.organization.*`; Better Auth enforces that the signed-in user's email matches the invitation.
  - **Self-service join code** — for students (bulk, no email). One rotatable code per org (`orgJoinCode` in `app-schema.ts`; PK = organizationId), TTL 14 days, always grants `student` (never a privileged role). An `enabled` flag pauses self-enrollment without discarding the code (toggle off → preview + join 404, code preserved for when it's switched back on; rotating re-enables). Managed at `/api/school/join-code` (GET current / POST rotate / PATCH `{enabled}`, school roles only); redeemed via public `GET /api/join/[code]` (preview) + `POST /api/join` (adds membership through `auth.api.addMember`, idempotent). Client pages: `/join` (code input) and `/join/[code]` (preview + confirm). Service: `server/utils/services/joinCode.ts` (unambiguous 8-char alphabet, no 0/O/1/I).
- **Extended school profile** — the Better Auth `organization` table only models `name`/`slug`/`logo`/`metadata`. Everything else a school fills in (contact, address, timezone/locale/currency, legal name + tax id, offered sports, description) lives in the app-owned **`orgProfile`** table (`app-schema.ts`; PK = organizationId, 1:1). Kept out of the auth table on purpose: it's app-domain data, must not bloat get-session/app-context payloads, and grows without re-running `pnpm auth:generate`. Read/written by `services/orgProfile.ts` (Drizzle directly — app-owned) via `GET`/`PATCH /api/school/profile` (school roles); each settings section PATCHes only its own keys. **Validation is one shared Zod schema** (`shared/org-profile-schema.ts`) — the single source of truth for the profile's rules: the server parses the PATCH body against it (`normalizeOrgProfilePatch` via `readValidatedBody`, `.partial()` so only present keys survive) **and** each settings card binds its section slice to `UForm :schema` (`profileSectionSchemas` in `app/utils/orgProfile.ts`), so form and API can never drift. The schema is parameterized by a **message resolver** (client → localized i18n error keys, server → raw stable codes that are never user-facing — server validation is defense-in-depth behind the form); section grouping (`PROFILE_SECTION_FIELDS`) and the flat form-state shape (`ProfileFormState`) derive from it too. Constants + pure format helpers (sports, locales, email/url/phone checks) stay in `shared/org-profile.ts`. **Deliberately added later in settings, not at onboarding** (better UX; a future notification system integrates with timezone/locale/contactEmail) — with one exception: the **operational regional defaults** (`country`/`timezone`/`currency`/`locale`) are silently **seeded at school creation** from zero-permission browser signals (`Intl…timeZone` + `navigator.language`), so a school doesn't start as Poland regardless of location. The derivation is the pure, unit-tested `deriveRegionalDefaults` in `shared/regional.ts` (curated timezone→country + country→currency tables, degrading field-by-field to `REGIONAL_FALLBACK`, which is also the server-side `PROFILE_DEFAULTS`). No modal, no GPS; the UI language itself is separately handled by i18n `detectBrowserLanguage`. `name`/`slug`/`logo` still mutate through Better Auth (`authClient.organization.update`). **Logo uploads** go to S3-compatible storage: `POST /api/school/logo` (multipart, ≤2 MB, png/jpeg/webp) returns a URL the client then persists as `logo` via `organization.update`.
- **Extended membership metadata — `memberProfile`** (app-owned sidecar to Better Auth's `member`, PK = memberId, 1:1 — the member analogue of `orgProfile`). Holds what the auth table doesn't: **`status`** (`active`/`suspended`/`archived` — the membership lifecycle; a three-state enum, not a single `archivedAt` timestamp, and NOT `auth.api.removeMember` — archiving keeps the row + all history), a **`canCoach` capability** (an owner/admin who also teaches can be assigned as a coach — orthogonal to the governance role, mirroring the org `types[]` model), and staff-only CRM fields (`notes`, `tags[]`). **Absence of a row = the column defaults**, so existing members need no backfill — the service coalesces. Written by `services/memberProfile.ts` with Drizzle directly (rule 4 is scoped to Better-Auth tables), **every query scoped by `organizationId`, never memberId alone** (tenant isolation, covered by server tests). The query is parsed by the pure `parseMemberDirectoryQuery` (shared, unit-tested; lenient — drops unknown values). **The flat `GET /api/school/members` is deliberately kept unchanged** (returns `OrganizationMember[]`) — the schedule + court-detail coach/student pickers depend on its shape; only `/school/members` migrated to the directory. **Phase 3 (done):** the member cockpit `app/pages/school/members/[id].vue` (single page, 2-column card grid — identity · access & lifecycle · staff notes/tags; directory rows link to it), fed by `GET /api/school/members/[id]` (the static `directory`/`export` siblings win over this dynamic route in Nitro) and mutated by `PATCH /api/school/members/[id]/profile` (validated via the shared schema; the service enforces an **owner-status guard** — the owner can never be suspended/archived, preventing lockout — and the UI also locks role+lifecycle for the owner and for yourself). Includes the `canCoach` capability toggle (owner/admin) and the `MemberStatus` lifecycle (active/suspended/archived — **archive = roster hygiene today**; auth enforcement of `suspended` blocking access is a later phase). **Phase 4 (done): governance is server-authoritative + audited.** Role change (`PATCH /api/school/members/[id]/role`) and removal (`DELETE /api/school/members/[id]`) route through thin handlers that call `auth.api.*` (rule 4) **behind guards** — the owner's role/removal is protected (last-owner / lockout safety) and you can't act on your own membership — replacing the client's direct `authClient.organization.*` calls, so guards can't be bypassed. Every governance transition (role/status/canCoach/removal) is written to an append-only **audit log**: `auditLog` (`app-schema.ts`, product-neutral **core**) + `services/audit.ts` — actor/target are **denormalized (no FK)** so the trail outlives a member's removal, `data` snapshots the actor's name, and `action` is a stable `AUDIT_ACTIONS` key (`shared/audit.ts`) rendered client-side (rule 5). `recordAudit` is **best-effort** (a failed trail write never fails the governance action it records). The cockpit shows a per-member **Activity timeline** (`GET /api/school/members/[id]/audit` → `listMemberAudit`, scoped by org). The directory table **sorts by clicking column headers** (server-side). **Phase 4b (done): the `suspended`/`archived` lifecycle is enforced.** `listUserMemberships` coalesces the sidecar status onto every `Membership`, so `requireActiveMembership` **403s a non-active membership** (`MEMBERSHIP_INACTIVE`) *before* the role check, and the client (`resolveAreaRedirect` + the `resolve-home` middleware) routes a non-active active-membership to the terminal **`/access-paused`** page (uses the `auth` layout — which already exposes sign-out — and carries **only** the `auth` middleware, no area guard, so there's no redirect loop; it offers switching to another school where the user is still active). Enforcement is a strict **additive branch**: a member with no sidecar row coalesces to `active`, so existing flows are untouched (verified — the full 124-test server suite passes against Postgres). The owner can never be non-active (write-guarded), so a school can't be locked out. **Phase 4c (done): `canCoach` is wired into scheduling.** The pure `canMemberCoach({ role, canCoach })` (`shared/member-profile.ts`, unit-tested) = *role `coach`, OR an owner/admin explicitly granted the capability* — deliberately **orthogonal to `status`** (callers check that separately, so "not set up to coach" and "access paused" stay distinct errors). It is the single source of truth for both ends: the flat `GET /api/school/members` now carries `status` + `canCoach` (`listOrganizationMembers` joins the sidecar), the schedule + court-detail pickers offer only `status === 'active' && canMemberCoach(m)` (students likewise filtered to active), and the schedule service's `requireCoach` enforces the same rule server-side (`SCHEDULE_COACH_INVALID_ROLE` / new `SCHEDULE_COACH_INACTIVE`). Because this **tightened** an existing rule (any non-student could previously coach), migration **0016 is a hand-written idempotent data backfill** granting `canCoach` to every owner/admin already assigned as a coach — so no pre-existing assignment silently became un-editable or vanished from the picker. **Phase 4d (done): the org-wide audit feed + ownership transfer.** `listOrgAudit` + `GET /api/school/audit` power `/school/audit` (sidebar *Activity log*) — the only surface where an event about an **already-removed** member stays visible (their per-member timeline is unreachable once gone), which is the point of a trail. It is **keyset**-paginated, not OFFSET: the log is append-only, so entries landing at the head would make an OFFSET pager skip/repeat rows; the cursor encodes `(createdAt, id)` and the predicate is built from **typed drizzle operators** (`or(lt(createdAt), and(eq(createdAt), lt(id)))`) — a raw `(created_at, id) < (…)` row-value tuple makes the driver guess the bind type for a bare `Date` and mis-serialize it against the plain `timestamp` column (caught only by running the suite against real Postgres). Every emit site snapshots `targetName` into `data` so a feed row names its subject without a join and keeps its historical wording. Rendering is shared by the cockpit + feed via `app/utils/audit.ts` (`auditActionText`/`auditActionIcon`; unknown actions degrade to a generic line). **Ownership transfer** — `POST /api/school/members/[id]/owner`, **owner-only** (a school-role guard is not enough: an admin must never seize or hand off ownership) and the only path that mutates an owner's role at all (`role.patch` refuses owners). Better Auth has no native transfer, so it is two `updateMemberRole` calls that cannot share a transaction; the **order is the safety property** — promote the target FIRST, then demote the outgoing owner, because the reverse could leave the school with *no* owner. A failed demotion is reported explicitly (`MEMBER_OWNER_DEMOTE_FAILED`, two owners = benign + recoverable) rather than hidden. **Phase 5 (done): Academy people-analytics.** The cockpit is now **tabbed** (mirroring the courts cockpit; panels stay mounted via `v-show`): **Overview** (core — identity/access/CRM/audit) vs **Academy** (what the person actually does here). `services/memberAcademy.ts` (Academy, composition-only) answers *hours + which groups* through two lenses — `teaching` (gated on the **capability** `canMemberCoach`, so an owner/admin who teaches gets one) and `learning` (students) — by reusing `listSessions({ coachMemberId })` / `listStudentSessions`; a member is never both. **The time math is not new**: `computeUtilization`'s bucketing was extracted into the exported, product-neutral `computeIntervalLoad` (+ `clampedMinutes`) in `shared/utilization.ts`, so a person's heatmap and a court's heatmap are literally the same engine and can't drift (the courts behaviour is unchanged — its tests pass untouched). Cancelled occurrences never count as taught/trained time. `attendanceRate` (`shared/member-academy.ts`, unit-tested) **excludes `excused` from both sides** — an excused absence is sanctioned, so counting it would make the number punitive — and returns `null` (renders "—") when nothing is marked, never a fake 0%. `GET /api/school/members/[id]/academy?from&to` (school roles, rolling 30-day default) → `MemberAcademyDto`. UI `components/school/members/AcademyPanel.vue` deliberately reuses the court panel's visual language (period selector, KPI tiles, sequential single-hue heatmap + legend): magnitudes are **tiles, not charts**, groups are an **identity list ordered by commitment** (never a pie), and the series colour is a **mark beside** the name — never the text colour (per the dataviz skill).
- **Guardians & minors (`memberGuardian`, migration 0017)** — a racket school teaches mostly children, so "who do we call?" is a first-class model, not a note. **CORE, not Academy**: it describes a *person*, not a lesson, so it lives beside the member sidecar and moves with the core. `memberProfile.dateOfBirth` is a **`date`, not a timestamp** — a birthday must not shift across timezones — and minor status is **derived on every read** (`isMinor`/`calculateAge` in `shared/member-guardian.ts`), never a stored flag that would go stale the day a birthday passes. `calculateAge` is calendar-correct (a birthday that hasn't come round yet this year doesn't count — the bug that silently ages 17-year-olds into adults) and returns `null` for a malformed/impossible/future/absurd date, so one check in `memberProfileSchema` covers every way a DOB goes wrong. A guardian is a **contact record, not an account** (a parent must be reachable long before, and often without ever, signing up); linking one to a `user` for a parent portal is a later additive column, not a seam carried unused. **Invariants:** a guardian must have a phone **or** an email (`hasReachableChannel` — a contact you can't reach isn't one; enforced by `guardianCreateSchema`, and re-checked against the *merged* record on PATCH in the service, mirroring the courts "effective sport" split); at most **one primary** per member — the DB owns that truth via a **partial unique index** (`ON (member_id) WHERE is_primary`) while `services/memberGuardians.ts` keeps it true by demoting the incumbent in the same transaction; the first guardian is promoted automatically, and deleting the primary promotes the longest-standing survivor so a member is never left with contacts but nobody to call first. **`needsGuardian` (minor + zero guardians) is surfaced as a warning, never enforced as a block** — a student is routinely added before the paperwork arrives, and refusing that would push the school back to the spreadsheet this product replaces. REST `GET/POST /api/school/members/[id]/guardians`, `PATCH/DELETE .../guardians/[guardianId]` (school roles — this is PII). UI: `components/school/members/GuardiansCard.vue` on the cockpit's Overview tab + a minor badge on the identity card. - **Consents (`memberConsent`, migration 0018)** — RODO/GDPR permissions, CORE like guardians. **`CONSENT_TYPES` is deliberately just `image` + `marketing`**: only purposes that are *genuinely* consent-based. Running the lessons a family signed up for is processed on the basis of the **contract** (art. 6(1)(b)), so a "data processing consent" would be a legal error with teeth — consent is withdrawable at will (art. 7(3)), so honouring a withdrawal would have to stop the service mid-term. A unit test guards the omission. **The row is current state; the audit trail is the history** (`member.consent_granted` / `member.consent_withdrawn`) — together they satisfy art. 7(1) accountability without making "may we, right now?" expensive. **Withdrawal never deletes the row and never clears `grantedAt`** — that timestamp is the evidence of the period during which processing *was* lawful — and it's one click, asking for nothing (art. 7(3)). **Absence of a row = `unknown` ("never asked"), never `withdrawn`**: both block use, but one is paperwork to chase and the other a decision to respect; `consentState` degrades an unrecognised stored value to `unknown`, never to `granted` (failing open would mean processing without consent). `mayUse(state)` is the only question the app should ask — silence is never permission. **A minor's consent must come from one of THEIR guardians** (checked in the service against the stored `dateOfBirth`, which the static schema can't see — the same context-rule split as courts' "effective sport"); an adult consents for themselves. `grantedByName` is snapshotted because accountability must outlive the guardian record; `documentVersion` records *what* was agreed to, since a changed clause invalidates old consent. REST `GET /api/school/members/[id]/consents`, `PUT .../consents/[type]` (school roles). UI: `components/school/members/ConsentsCard.vue`. The **roster-level compliance-gap report** built on this + guardians now ships (see "Compliance report"). Still later: a parent portal (guardian↔user link).
- **Reads vs mutations:** reads via services + `/api/*` (`membership.ts` service). Better Auth org/member/invitation mutations go via `authClient.organization.*` (client) or `auth.api.*` (server) — never direct Drizzle writes to those tables (rule 4). App-owned tables like `orgJoinCode`, `orgProfile` and `memberProfile` are written by their service directly.
- **Gotcha — Nuxt async context:** the unctx transform covers `app/middleware/*` and plugins only. Never call `navigateTo` (or other Nuxt composables) after an `await` inside `app/utils/*` — compute the redirect target in the util, call `navigateTo` from the middleware file.
- **Gotcha — `auth` CLI:** `server/utils/auth.ts` and everything it imports (e.g. `services/membership.ts`, `shared/permissions.ts`, `services/notifications.ts`) is loaded by the `auth` CLI **outside Nuxt** — those files need explicit imports (no auto-imports, no Nuxt aliases).

## Courts (facility core)

A facility's courts/tables, managed at `/school/courts` (school roles). **This is facility-core, NOT Academy** — deliberately product-neutral so the future Courtto marketplace books the *same* rows: nothing here references lessons/coaches/students. When the core is extracted to `packages/core`, courts move with it.

- **Model — app-owned `court`** (`app-schema.ts`; FK → organization, cascade). `archivedAt` is the lifecycle axis (**soft-delete**, so schedule/booking history never orphans). There is deliberately **no operational `status` column** — a court is either on the active roster or archived; *time-bounded* unavailability (maintenance/closures) is a `reservation` block (see Scheduling), not a court flag. (An earlier cosmetic `active`/`maintenance` status was removed in migration 0011: it never enforced anything, and blocks + archive cover the real needs — indefinite closure = a long/repeat block or archive.) Name is **case-insensitively unique among active courts** (partial unique index `WHERE archived_at IS NULL`, so archiving frees the name). `sortOrder` drives display order (drag-reorder). `bookable` is a **seam** for Courtto (unused today, no UI). Written by `services/courts.ts` with Drizzle directly — **every query scoped by `organizationId`, never id alone** (multi-tenant isolation, covered by server tests).
- **Discipline is validated ⊂ `orgProfile.sports`** on write (defense-in-depth; the builder only offers declared sports). A court's **white-line pattern is derived from `sport`, never stored** — only surface/line colours are per-court.
- **Shared domain — `shared/courts.ts`** (pure, no Nuxt/Node; imported by server validation + client form + the SVG renderer): `COURT_SPECS` (per-discipline geometry in metres — the line pattern), unit (`court`/`table`), `SURFACES_BY_SPORT`, colour presets/defaults, and the low-level validators. Unit-tested (`test/unit/courts.test.ts`); server-tested against Postgres (`test/server/courts-service.test.ts`: tenant isolation, sport-not-offered, name uniqueness, surface-drop-on-sport-change, reorder, hard-delete).
- **Validation is one shared Zod schema** (`shared/courts-schema.ts`, mirroring `org-profile-schema.ts`): the builder binds it to `UForm :schema` and the server parses the POST/PATCH body against the same rules (`courtCreateSchema` full / `courtPatchSchema` partial), so form and API can't drift. Parameterized by a message resolver (client → localized keys, server → raw codes). Two **context-dependent** rules stay in the service, not the static schema: the discipline must be ⊂ `orgProfile.sports`, and the surface must be valid for the *effective* sport (which, on a partial update, may be the stored one).
- **Lifecycle — archive vs delete.** `DELETE [id]` **archives** (soft — `archivedAt`, reversible, keeps history); `DELETE [id]?purge=1` **hard-deletes** (`deleteCourt`, irreversible, will cascade to future schedule/booking/group FKs — UI guards it with a warning); `PATCH [id] {restore:true}` restores. Archived courts **stay visible** in the roster (dimmed, in their own "Archived" section), never hidden.
- **REST** `server/api/school/courts/*`: `GET` (`?includeArchived=1`), `POST`, `GET/PATCH/DELETE [id]`, `PATCH reorder`. The static `reorder` route wins over `[id]` in Nitro; on the client, typed `$fetch` intersects a dynamic `/courts/${id}` path with the sibling `reorder` route, so a `DELETE` there needs the URL annotated `: string` to widen the method type.
- **Maintenance windows / closures (court blocks)** — taking a court out of service for a range is a **standalone core `reservation`** (no lesson attached), so it's facility-CORE, not Academy: `kind` ∈ `COURT_BLOCK_KINDS` (`maintenance` | `blocked`, in `shared/reservation.ts`). It needs **no schema/migration** — the reservation table already carries `kind`/`title`/`note`, the kind-agnostic court-overlap `EXCLUDE` + `CHECK (ends_at > starts_at)` already enforce it, and lesson creation's `assertNoCourtConflict` already scans all non-cancelled reservations, so a block **automatically blocks lessons and vice-versa** (proven both ways in `test/server/court-blocks-service.test.ts`). Service `services/courtBlocks.ts` (`createCourtBlock`/`listCourtBlocks`/`deleteCourtBlock`) resolves wall-clock inputs to instants in the org timezone (like the schedule), pre-checks the court is free (EXCLUDE is the race-safe backstop), and **`deleteCourtBlock` is constrained to block kinds + refuses any reservation a `lessonSession` points at**, so it can never orphan a lesson. One shared Zod schema (`shared/court-block-schema.ts`, mirrors the others). **REST** `POST /api/school/courts/[id]/blocks`, `DELETE /api/school/courts/[id]/blocks/[blockId]`; the list is folded into `GET /api/school/schedule` → `{ sessions, blocks }`. **UI:** launched from the court card's action menu (opt-in `block-action` prop → `SchoolCourtsBlockSlideover`, all-day or timed), rendered on the schedule calendar as a tinted "unavailable" band behind lessons (`blockDaySpan` clamps a multi-day block per column; day+week only, not agenda), click a band → remove.
- **Visual builder** — `components/courts/Diagram.vue` (`<CourtsDiagram>`) is the product-neutral top-down SVG (surface fill + white lines + walls for enclosed disciplines), reused in the roster tile (`<CourtsCard>`) and the two-pane `<SchoolCourtsFormSlideover>` (form ⟷ live preview). Client dates arrive serialized, so the UI binds against `CourtView` (string dates), not the server `CourtDto` (`Date`). `<CourtsCard>` stays product-neutral: its Academy affordances are **opt-in, off-by-default props** (`schedule-action` → deep-links to `/school/schedule?court=<id>`, which seeds the calendar's court filter from the query and mirrors it back to the URL; `block-action` → opens the maintenance-block slideover; `to` → makes the title a link to the detail page), so the marketplace reuses the tile read-only without surfacing lesson/maintenance concepts.
- **Pages.** The roster is `pages/school/courts/index.vue` (`/school/courts`; each card has an explicit *Details →* button, gated on the neutral `to` prop, not just a title link); the per-court hub is `pages/school/courts/[id].vue`. **Detail page = a per-court cockpit, organized into TABS** (Overview / Schedule / Utilization — kept mounted via `v-show` so the calendar's view/anchor state survives switching and nothing refetches; no long scroll). Overview (diagram + `courtMetaParts` line + maintenance card) · this court's schedule (reuses `<ScheduleToolbar>` + `<ScheduleCalendar>`/`<ScheduleAgenda>`, **actionable when not archived** — click-empty/`Add lesson` opens the shared `<ScheduleFormSlideover>` prefilled to this court, drag reschedules, lesson click opens `<ScheduleSessionSlideover>`; only the heavier whole-series edit routes to `/school/schedule?court=<id>`) · a **Maintenance & closures** card (its own forward-window `GET /api/school/courts/[id]/blocks` list, add/remove). There is deliberately **no "open in schedule" button** — you act in place; the sidebar's *Schedule* is the cross-court view, and the roster card's `schedule-action` (the filtered multi-court view) is a distinct affordance kept there. The court's slice is server-filtered: `listSessions`/`listCourtBlocks` take an optional `courtId`, exposed as `GET /api/school/courts/[id]/schedule` → `{ sessions, blocks }` (a dynamic fetch URL matches several typed routes, so annotate the response generic). `<ScheduleFormSlideover>`'s `prefill` accepts an optional `sport` so opening on a court whose discipline isn't the first offered still preselects it (its `startLocal` is optional too → default start). Court lifecycle (archive/restore/purge) lives in the **`useCourtActions()`** composable shared by both pages (HTTP + toast; the page decides refetch vs navigate-away). `parseInstant` (from/to query parsing) is a shared `server/utils/query.ts` helper.
- **Zones are first-class** (`courtZone` table, `app-schema.ts`; NOT a free-text column — an earlier `court.zone` text was promoted in migrations 0012/0013, a data-preserving expand-contract: 0012 adds the table + `court.zoneId` FK and backfills distinct names into rows, 0013 drops the old column). A zone is a named, orderable facility area/hall; `court.zoneId` FK is **`onDelete: 'set null'`** so deleting a zone **ungroups** its courts, never deletes them. Name is case-insensitively unique per org (partial unique index → `COURT_ZONE_NAME_TAKEN`). Service `services/courtZones.ts` (`listZones` with each zone's active `courtCount`, `createZone`/`updateZone`/`reorderZones`/`deleteZone`, + `zoneBelongsToOrg` which the court service calls to validate `court.zoneId`). **REST** `server/api/school/zones/*`: `GET`/`POST`, `PATCH`/`DELETE [id]`, `PATCH reorder` (static route wins over `[id]`, mirroring courts). **UI:** the roster **sections courts by zone** (named zones in order, empty ones omitted, ungrouped last; headers appear only once a grouping exists) with drag-reorder scoped **within** a section; `<SchoolCourtsZonesSlideover>` (opened from the roster's "Zones" button) is the create/rename/drag-reorder/delete manager; the court builder's zone **picker** and the detail page's zone badge resolve names from the same `GET /api/school/zones` (shared `school:zones` key). The schedule's `<ScheduleFilters>` has a **zone multi-select** too: a session/block/column has no zone of its own, so the page passes a `court→zoneId` map and `sessionMatchesFilters`/`courtMatchesZones` resolve it (`ScheduleFilterState.zoneIds`). The zone picker's "no zone" option (and any optional-id `USelectMenu`) uses a **`NO_ZONE_VALUE`/`NO_COACH_VALUE` sentinel, never `''`** — Reka's select reserves the empty string for clearing and *throws* on an item valued `''` (it froze the whole builder slideover once). Zone is NOT in `courtMetaParts` — it's a grouping, not inline metadata.
- **Utilization analytics** — a court's occupancy over a rolling window, computed from the **core `reservation` primitive** (facility-CORE, product-neutral): it splits **usage** (demand — `lesson` today, a Courtto `booking` tomorrow; `isUsageReservationKind`) from **downtime** (maintenance/closure blocks), so a future marketplace booking counts automatically with **zero analytics change**. The math is the pure, unit-tested `computeUtilization` in **`shared/utilization.ts`** (buckets each usage interval into a weekday×hour heatmap in the org zone by walking hour boundaries; utilization % = usage-within-`FACILITY_OPERATING_HOURS` ÷ window capacity, clamped ≤ 100). Service `services/courtUtilization.ts` fetches the court's non-cancelled reservations and calls it; **REST** `GET /api/school/courts/[id]/utilization?from&to` → `CourtUtilizationDto`. **UI:** `<SchoolCourtsUtilizationPanel>` (the detail cockpit's *Utilization* tab) — a 7/30/90-day selector, KPI tiles labeled in **Academy terms** (occupancy% / lesson hours / sessions / maintenance — NOT "bookings"; the neutral core still counts a future Courtto `booking`, but it isn't surfaced until the product exists), and a **weekday×hour demand heatmap** (single-hue sequential brand-green ramp via `heatmapCellClass` — CVD-safe by construction; per dataviz skill). Display helpers (`formatHours`/`heatmapCell`/`weekdayLabels`) live in `app/utils/utilization.ts`. Per-facility operating hours (vs the `FACILITY_OPERATING_HOURS` constant) and a facility-wide roll-up are the documented extensions.

## Scheduling (the lesson calendar)

The heart of Academy — lessons on courts over time. Built in phases (data model → single lessons + conflicts → recurrence with exceptions → enrolment + attendance → visual calendar); each phase went through adversarial review + fixes, and all six schedule tables + the calendar are fully covered by unit + live-Postgres server tests.

**Two layers, kept physically separate (like courts vs Academy):**
- **CORE — `reservation`** (`app-schema.ts`): the product-neutral occupancy primitive, one court occupied for one `[startsAt, endsAt)` half-open range. The future Courtto marketplace will book these exact rows; it references nothing Academy. `bookedBy*` are marketplace seams. Core domain lives in **`shared/reservation.ts`** (`RESERVATION_STATUSES`, `RESERVATION_KINDS` — neutral-first, default `blocked` not `lesson` — and `rangesOverlap`). **`kind`** default is `blocked`; the Academy layer sets `kind='lesson'` explicitly.
- **ACADEMY — `lessonSeries` / `lessonSession` / `lessonException` / `enrollment` / `attendance`**: a lesson is always a *series* (rrule null = one-off) plus its materialized *sessions*, each pointing DOWN at one core reservation (`lessonSession.reservationId`, notNull). Core never FKs up to Academy. `shared/schedule.ts` holds the Academy constants + the DST-correct time/recurrence helpers.

**Time & DST (the trap):** a series stores WALL-CLOCK local `dtStart` ('YYYY-MM-DDTHH:mm') + an IANA `timezone` (snapshotted from `orgProfile.timezone` at create); occurrences are resolved to absolute **UTC instants** (`timestamptz`) at materialization, **per occurrence** in the zone (via `luxon` + `rrule`), so "every Monday 17:00" stays 17:00 local across a DST switch. `expandOccurrences` runs rrule in floating wall-clock then re-localizes each result; an RFC-5545 `UNTIL` is re-expressed in the same floating clock. Schedule time columns are `timestamp with time zone` (unlike the plain-`timestamp` audit columns elsewhere). Only DAILY-or-coarser recurrence is supported (`isSupportedRecurrence` — sub-daily would self-overlap and fan out).

**Conflict prevention (both hard, race-safe, per Q4):** two hand-added Postgres `EXCLUDE USING gist` constraints (Drizzle can't express EXCLUDE; both need `btree_gist`), each backed by a `CHECK (ends_at > starts_at)` so an empty range can't silently defeat the `&&` test: (1) **court** — `EXCLUDE (court_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE status <> 'cancelled'` on `reservation` (migration 0006); (2) **coach** — `EXCLUDE (coach_member_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE coach_member_id IS NOT NULL AND status <> 'cancelled'` on `lesson_session` (migration 0007), which the single-court constraint can't span (a coach clash crosses courts) — it works because the session's coach/time columns are DENORMALIZED, so no join back to the series. The service still runs friendly pre-checks (`assertNoCourtConflict`/`assertNoCoachConflict` return *which* occurrence) for the common case; the EXCLUDEs are the backstop that only fires on a genuine concurrent write. `courtOverlapViolation`/`coachOverlapViolation` branch on `error.constraint` (check coach FIRST — an unnamed 23P01 falls back to court) and unwrap Drizzle's `DrizzleQueryError.cause` via **`server/utils/pgError.ts`** (`pgErrorCode`/`pgErrorConstraint` — drizzle ≥0.36 wraps the PostgresError; a naive `error.code` check misses it).

**Recurrence + exceptions (RRULE + separate ledger, per Q2):** create materializes concrete `lessonSession` + `reservation` rows up to `MATERIALIZATION_HORIZON_DAYS` (rolling: recurring rolls from *now*, a one-off is its exact occurrence), bulk-inserted in one transaction. Single-occurrence edits are the iCalendar EXDATE/RECURRENCE-ID model: **`lessonException`** (unique `(seriesId, occurrenceStart)`, actions `cancelled|rescheduled|modified|skipped`) is the durable divergence ledger; a session's `overridden` flag + resolved (denormalized) `coachMemberId`/`courtId`/`startsAt` mean divergence is measured against the series template (`computeDivergence`) so a no-op edit doesn't flag it and moving back onto the anchor clears it. `cancelLessonSession`/`restoreLessonSession`/`updateLessonSession` re-check conflicts excluding the session's own reservation; `updateSeriesAssignment` propagates a coach/court change to future non-overridden sessions; `extendMaterialization` rolls one series' horizon forward (skips existing + exception occurrences; records court/coach skips as `skipped` exceptions rather than silently losing them — and on a 23P01 first checks `sessionExistsForOccurrence`, so a benign concurrent materialization of the *same* series never records a spurious skip; validates the court is still active). **Automatic horizon extension** is the Nitro scheduled task **`server/tasks/schedule/materialize.ts`** (`schedule:materialize`, wired in `nuxt.config.ts` `nitro.scheduledTasks`, nightly 03:15; needs `nitro.experimental.tasks`): its service `runMaterializationSweep` selects every active recurring series whose runway dropped below the refill threshold (`materializedUntil < now + 90d`, indexed by the partial `lesson_series_materialization_idx`) across ALL tenants and extends each — so a series is topped up roughly monthly, not every run. Bounded (per-run cap → `capped`), per-series failures are isolated (logged, never abort the sweep), and an in-process reentrancy guard prevents same-instance overlap. `extendMaterialization` is fully idempotent + race-safe, so concurrent sweeps are *safe* (just wasteful) — cross-instance single-flight (advisory lock / lease) is the documented horizontal-scaling seam, mirroring the realtime one. **Lifecycle contract:** deleting a session/series must also delete its reservation(s) transactionally — no DB cascade in that direction by design; normal cancellation flips both to `status='cancelled'` (freeing the court via the partial EXCLUDE) rather than deleting.

**Enrolment + waitlist + attendance (`services/enrollment.ts`):** a student enrols in a whole **series** (counts against `series.capacityMax`) or a single **session** drop-in (counts against `session.capacityMax ?? series.capacityMax`, together with the series' enrolees). Capacity is enforced under a **per-series `SELECT … FOR UPDATE` row lock** taken by every enrol/cancel, so concurrent enrolments can't both take the last seat; over capacity → `waitlisted` with a position; cancelling an *enrolled* seat promotes the first waitlisted in the same scope (status is re-read under the lock so a double-cancel promotes exactly once). Series and per-session waitlists are **independent queues** (deliberate). `attendance` (present/absent/excused/late, one row per `(session, student)`) can only be marked for **enrolled** attendees; `getSessionRoster`/`markAttendance` take an optional `asCoachMemberId` that requires the session be that coach's own.

**REST** — school (`AREA_ROLES.school`, `server/api/school/schedule/*`): `index` GET(list `?from&to`)/POST(create), `[id]` GET/PATCH(metadata)/DELETE(`?purge` hard-delete else cancel), `[id]/assignment` PATCH, `[id]/extend` POST, `[id]/enrollments` GET/POST, `enrollments/[id]` DELETE, `sessions/[id]` PATCH(reschedule/override, `{restore}`)/DELETE(cancel), `sessions/[id]/{roster GET, attendance PUT, enrollments POST}`. Coach (`server/api/coach/schedule/*`): `index` GET (own sessions, returns `{ sessions, timezone }`), `sessions/[id]/{roster,attendance}` (own only). Student (`server/api/my/*`): `schedule` GET (`{ sessions, timezone }`), `enrollments` POST (series XOR session self-enrol), `enrollments/[id]` DELETE (own only). Coach/student can't call `/api/school/*`, so their session feeds carry the school `timezone` alongside the sessions. Handlers stay thin (rule 1); every thrown `data.code` is localized under `error.codes.*` in both locales.

**Visual calendar (the "sells the product" UX)** — a custom resource grid (no calendar lib), `components/schedule/Calendar.vue` (`<ScheduleCalendar>`): **day view = courts as columns**, **week view = days as columns**; blocks positioned by local start on a fixed band, overlaps laid **side-by-side** (`computeLanes`), a reactive current-time line, native **drag-to-move** (preserves the grab point, no-op drops don't PATCH) and **click-empty-to-create**. Sessions on an archived/foreign court fall into an "Other" column (never dropped). `<ScheduleFormSlideover>` (create; binds the shared `scheduleFormSchema(t)` + a compact RRULE builder), `<ScheduleSessionSlideover>` (detail + reschedule/cancel/restore for school, roster+attendance for school/coach), `<ScheduleToolbar>` (prev/next/today + day/week), `<ScheduleBlock>`/`<ScheduleSessionBadge>`. Pure grid/time math + the string-dated `*View` types live in **`app/utils/schedule.ts`** (auto-imported, mirrors `app/utils/courts.ts`; unit-tested). Pages `/school/schedule`, `/coach/schedule`, `/my/lessons` follow the courts page skeleton (`UDashboardPanel`, `useLazyFetch` with a reactive `?from&to` range, `MotionReveal`, `toastError`). **Known limits:** drag-to-move/create are pointer-only (keyboard users use the Add/Reschedule buttons). Payments/pricing and public Courtto booking remain seams only.

## Transactional email

The outbound-mail layer — password reset (the V1 blocker) + additive staff-invitation emails. **CORE, product-neutral plumbing:** it knows nothing about lessons/coaches/students and moves with the core when Courtto is extracted.

- **Transport — `server/utils/mailer.ts`.** The one seam that keeps the provider swappable. Speaks plain SMTP via **`nodemailer`**, so nothing outside this file knows the provider: **Brevo's SMTP relay** in prod (chosen for **EU data residency + a DPA** — this app processes children's PII, so a US provider would reopen the GDPR/transfer question the guardian/consent models close), **AWS SES `eu-central-1`** as the documented scale-up (env-only change; you'd wire SES→SNS bounce handling yourself), **Mailpit** in dev. Mirrors `storage.ts`: a module-level lazy singleton, env via `node:process`, **no `useRuntimeConfig`, no factories** (rule 2). Explicit imports only — it's reachable from `auth.ts`, which the `auth` CLI loads outside Nuxt. Public surface is just `sendMail({ to, subject, html, text })` (+ `isMailerConfigured`, and a `setMailTransport`/`clearMailTransport` **test seam**).
- **Dev/unset behaviour is LOUD, never silent.** Unlike storage's quiet 503, an unconfigured mailer (`SMTP_HOST`/`MAIL_FROM` unset) falls back to a **console transport that prints the whole message — reset/invite link included — to the server log**. Rationale: a password reset that no-ops in dev is a broken flow you'd never notice; a visible one is completable by copy-paste. Point `SMTP_HOST=localhost SMTP_PORT=1025` at Mailpit for a browser inbox.
- **Content is a pure, server-only i18n catalog — `shared/email.ts`** (unit-tested by rendering to a string). **Deliberately NOT in `i18n/locales/*.json`:** this copy is only ever rendered server-side, so vue-i18n would ship every subject line and legal footer to every browser, and `auth.ts` (which calls the renderers) loads under the `auth` CLI *outside* Nuxt where vue-i18n isn't available. So it's a **server-side message catalog** (rule 5's intent, for text the client never sees) — pure (no Nuxt/Node), so it loads anywhere and is unit-tested directly. Holds `resolveEmailLocale`, the en/pl catalog, and `renderPasswordResetEmail`/`renderInvitationEmail` → `{ subject, html, text }` (branded inline-styled HTML + a plain-text alternative). **Every interpolated user value is `escapeHtml`-escaped** in the HTML body (school/inviter/recipient names are attacker-controlled).
- **Which language?** An **invitation** has org context → the school's `orgProfile.locale` (its documented default notification language). A **password reset** has none (the user may have zero or several orgs) → resolved from the **request**: the i18n cookie (`courtto_locale`) first, then `Accept-Language`, falling back to the app's `defaultLocale` (`en`). This split lives in `resolveEmailLocale`/`toEmailLocale`.
- **Composition service — `server/utils/services/email.ts`** (thin, auth-CLI-reachable): `sendPasswordResetEmail` (resolves locale from the request, renders, sends) and `sendMemberInvitationEmail` (reads `orgProfile.locale`, links to the existing **`/invite/[id]`** landing page, renders, sends). These **throw** on transport failure (honest for tests); the `auth.ts` wiring wraps each in try/catch (**best-effort — a mail failure never fails the auth flow**, mirroring the setup-notification emit), and Better Auth additionally swallows both via `runInBackgroundOrAwait`.
- **Password reset is Better-Auth-native.** `emailAndPassword.sendResetPassword` is wired; Better Auth builds the tokenized `url` (its `/reset-password/:token` callback validates the token, then redirects to our page with `?token=` or `?error=INVALID_TOKEN`). Pages `app/pages/{forgot-password,reset-password}.vue` (on the `auth` layout, like login) drive `authClient.requestPasswordReset({ email, redirectTo: '/reset-password' })` and `authClient.resetPassword({ newPassword, token })`; login links to forgot-password. **Enumeration-safe by construction:** Better Auth returns an identical `200` whether or not the account exists (with a timing-attack guard), so `/forgot-password` always shows the same "check your inbox" confirmation — verified in `test/server/email-service.test.ts` (a ghost email sends no mail, a real one emails a token that actually resets). **Rate limiting** is Better Auth's built-in special rule (3 requests / 60s on `/request-password-reset`), active in production (off in dev/test).
- **Notifications are NOT wired to email yet** (that's the next phase, gap #2) — the mailer is designed so `services/notifications.ts` *can* call `sendMail` later, but no unused hook was added now (no-inert-features doctrine).
- **Verification:** unit (`test/unit/email.test.ts` — locale resolution, template render + HTML-escaping) + server (`test/server/email-service.test.ts` — recording transport, real reset flow end-to-end, invitation wiring, enumeration). **Never sends real mail** — tests inject a recording transport via `setMailTransport`.

## Notifications & realtime

Per-user notification inbox surfaced as the bell in the dashboard navbar (`components/AppHeaderControls.vue` bundles `NotificationBell` + locale + theme; every area page's `#right` slot renders that one component). Sorted newest-first.

- **Model — per-user rows, optionally org-tagged.** App-owned `notification` table (`app-schema.ts`): each row is one recipient's copy with its **own** `readAt`/dismissed state (never shared across users). `organizationId` (nullable, cascade) tags the school context; the bell scopes to **active org + account-level (org-less)** items so a multi-school user never sees two schools' contexts mixed. `type` (stable machine key) + JSON `data` only — **never store localized text** (rule 5); the client renders `notifications.types.<type>.{title,body}` with `data` interpolated, falling back to `notifications.fallback.*` for unknown types. `link` deep-links the bell.
- **Read state** = "seen in the bell". Opening the popover marks the whole scope read (`POST /api/notifications/read`), clearing the `UChip` unread badge.
- **Dismissible vs system-managed.** `dismissible` (default true) rows get an `x` and are wiped by "clear all". **System notifications** (`SYSTEM_NOTIFICATION_TYPES` in `shared/notifications.ts`) are `dismissible: false`: no `x`, skipped by clear-all, and **resolved by a condition, not a click** — the system owns their lifecycle. They carry a `dedupeKey` (partial-unique with `userId`) so they're created at most once. There is deliberately **one** such type today.
- **First notification — `org.setup_incomplete`.** Emitted to the owner from Better Auth's `organizationCreation.afterCreate` hook (`auth.ts`, best-effort — never fails org creation). Resolved (deleted for the whole org) the moment the profile becomes complete, in `POST /api/school/profile`.
- **Org readiness is derived, not stored.** `computeProfileCompletion(profile)` in `shared/org-profile.ts` (pure, unit-tested) is the single source of truth — a stored boolean would drift. Required-to-operate fields: `REQUIRED_PROFILE_FIELDS` = `contactEmail`, `sports` (≥1), `city`, `country` (operational fields like timezone/locale/currency carry safe defaults, so they never block). This gates the setup notification **and** drives the readiness checklist at the top of `/school/settings` (`components/school/SetupChecklist.vue`, computed from the persisted `baseline` so it resolves in step with the notification — both on save, never on unsaved edits; each item deep-links to its settings section).
- **Service** `services/notifications.ts` (Drizzle directly — app-owned; explicit imports, reachable from the `auth` CLI): `createNotification` (dedupes via `onConflictDoNothing`), `getNotificationFeed`, `markScopeRead`, `dismissNotification` (guarded to owner + dismissible), `clearNotifications`, plus the `org.setup_incomplete` emit/resolve pair. REST: `GET /api/notifications` (feed + unread count), `POST /api/notifications/read`, `DELETE /api/notifications/[id]`, `DELETE /api/notifications` (clear all). All scope via `getActiveScope(event)` (`org.ts`).
- **Realtime — Nitro built-in WebSocket (crossws).** Enabled by `nitro.experimental.websocket` in `nuxt.config.ts`. Handler `server/api/notifications/ws.ts` (`defineWebSocketHandler`) authenticates the peer once from its session cookie (`auth.api.getSession`) and registers it by user id in an **in-process** singleton (`server/utils/realtime.ts`, `publishToUser`). `createNotification` nudges the user's peers; the client (`plugins/notifications.client.ts`) reconnects with backoff and just calls `refreshNotifications()` on any message. **Realtime is an enhancement, never the source of truth** — the REST feed is authoritative, so a dropped socket degrades to fetch-on-load and self-heals. Known limit: the registry is per-process; horizontal scaling needs a Redis / Postgres LISTEN-NOTIFY fan-out behind `publishToUser` (the single seam).
- **Client** `composables/useNotifications.ts` (keyed `useFetch`, optimistic mutate + reconcile) is the single client source; `clearNotificationsCache()` runs on every auth transition (`useSignOut`) so the previous user's notifications don't leak into the next session in the same tab (mirrors `clearAppContext`).
- **Lesson events — the operational pipe (`services/lessonNotifications.ts`).** The events that make the product the school's system of record: `lesson.cancelled`, `lesson.rescheduled`, `lesson.reminder`, `enrollment.waitlist_promoted`. Each fans out to **both** the in-app bell **and** email (localized in the school's `orgProfile.locale`, reusing `shared/email.ts` + the mailer). **Recipients:** the session's enrolled *active* students + the assigned coach; and — the decision that matters for a kids' school — the **primary guardian (by email) of any minor** student (guardians have no account, so email only, no bell). The service resolves recipients itself (scoped by `organizationId`) and every public function is **best-effort** — it swallows its own errors, and per-recipient delivery is isolated, so a notification failure never fails the cancel/reschedule/enrol that triggered it. **Emit points live in the mutation services, post-commit** (`cancelLessonSession`/`updateLessonSession` in `schedule.ts` — reschedule only when the *time* actually changed; the waitlist promotion inside `cancelEnrollment` in `enrollment.ts`, whose public return contract is unchanged), so **every** call path (schedule page, court cockpit, future bulk) notifies without the handlers repeating it. **Reminders** are the nightly-pattern scheduled task `server/tasks/schedule/reminders.ts` (`schedule:reminders`, hourly): `runLessonReminderSweep` selects every upcoming lesson in the next ~24h across ALL tenants and reminds its students+guardians. **Idempotency** rides `createNotification` (now returns whether it actually inserted): the student's reminder bell row is a per-`(user, session)` dedupe key, and the email (student + guardian) is sent only when that row is newly created — so overlapping hourly windows never double-send. Bounded per run; per-session failures isolated; concurrent sweeps are safe (cross-instance single-flight is the scaling seam, mirroring the materialization sweep). The bell copy is deliberately date-free (a glanceable nudge + deep link); the **email** carries the exact wall-clock time, resolved in the school's IANA timezone. Client rendering (icon + `notifications.types.lesson.*` copy) is in `NotificationItem.vue`, per rule 5. **Not yet wired:** whole-series cancellation and coach reminders (documented follow-ups, deliberately out of this phase to bound email volume).

## Observability & health

The eyes on production. **CORE, product-neutral plumbing** — it moves with the core when Courtto is extracted. Built because the email + notification layers are deliberately **best-effort (swallow-and-log)**: without a place those swallowed failures are seen, a broken reset email or a parent notification that never sends is invisible in prod.

- **The seam — `server/utils/monitoring.ts`.** One entry point for every server-side incident: `captureError(error, context?)` / `captureMessage(level, message, context?)`. Mirrors `mailer.ts`/`storage.ts` — a module-level lazy singleton, env via `node:process`, **no `useRuntimeConfig`, no factories** (rule 2), explicit imports (reachable from `auth.ts`, which the `auth` CLI loads outside Nuxt). Provider-neutral by design: every event is always emitted as a **structured JSON line** to the server log (parseable by any drain), and when `OBSERVABILITY_WEBHOOK_URL` is set it's **also** POSTed as JSON (fire-and-forget) — point it at a log drain, a Slack webhook, or a function that forwards to Sentry/Datadog. Wiring a real vendor SDK later is a **one-file swap of the default sink**; a real Sentry/Datadog adapter is a documented follow-up, deliberately not a half-wired dependency now (no-inert-features). **Reporting never throws or blocks** — an observability failure that cascaded into the code it observes would be worse than the incident. `context` carries safe structured fields (`scope`, `organizationId`, `path`) — never secrets or request bodies. Test seam: `setMonitoringSink`/`clearMonitoringSink` (a recording sink, exactly like the mailer's).
- **Global safety net — `server/plugins/monitoring.ts`.** A Nitro `error` hook captures every **unhandled** server error (5xx / uncoded) with request context. Expected app errors (4xx `createError`s — validation/auth/not-found) are normal control flow and are **not** reported, so the signal doesn't drown in routine 403s.
- **The wired blind spots.** The previously-silent `console.error` swallows now report through `captureError` with a `scope`: the mail sends + setup-notification emit (`auth.ts`), the audit-trail write (`services/audit.ts`), the lesson-notification fan-out (`services/lessonNotifications.ts`), and the materialization sweep's per-series failures (`services/schedule.ts`). Each stays best-effort — capture replaces the log, never the swallow. (The mailer's unconfigured-provider `console.warn` stays as-is: a dev-mode expected state, not an incident.)
- **Readiness — `GET /api/health`.** Public (no auth), thin handler over `services/health.ts` `checkDatabaseHealth` (one `SELECT 1`). 200 `{ status:'ok', db:'up' }` when the DB is reachable, 503 `{ status:'error', db:'down' }` otherwise; the body is deliberately minimal so it never leaks internals. For LB / container liveness+readiness probes.
- **Still seams (not built — enterprise HA):** a real vendor adapter (Sentry/Datadog), request-level tracing/correlation ids, metrics/counters (inert without a backend), and — the big one — the app is still **single-instance** (the realtime registry is per-process and the sweeps have no cross-instance lock; see Notifications/Scheduling). Horizontal scaling needs a Redis/Postgres-LISTEN fan-out + a distributed lock or job queue before it.
- **Verification:** unit (`test/unit/monitoring.test.ts` — event shape, non-Error normalization, never-throws-even-if-the-sink-throws) + server (`test/server/health-service.test.ts` — the readiness `SELECT 1` really executes against Postgres).

## Billing & subscriptions

How the app makes money: the **school (organization) is the paying tenant**, on a SaaS subscription to Courtto. **CORE, product-neutral plumbing** — it references nothing Academy and moves with the core when Courtto is extracted. Built on the **official Better Auth Stripe plugin** (`@better-auth/stripe` + `stripe`), because auth already runs on Better Auth + the `organization` plugin and this natively scopes a subscription to an org (`referenceId = organizationId`).

- **Plugin wiring — `server/utils/billing-config.ts`.** The one file that knows the Stripe SDK. Mirrors `mailer.ts`/`storage.ts`: env via `node:process`, a module-level `stripeClient`, **no `useRuntimeConfig`, no factories** (rule 2), explicit imports (it's reachable from `auth.ts`, which the `auth` CLI loads outside Nuxt). Exports the configured `stripe` plugin (registered in `auth.ts` `plugins`) + `isBillingConfigured()`. Env (all optional, **plain, no prefix**): `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_STARTER`, `STRIPE_PRICE_PRO`. **`authorizeReference` is owner-only** (like ownership transfer — an admin must never move money): it verifies the caller owns the org whose subscription they act on (`isOrgOwner`). `createCustomerOnSignUp: false` — the Stripe customer is created lazily at first checkout, so signup never makes a network call. Webhook is auto-mounted at **`/api/auth/stripe/webhook`** (the plugin verifies the signature).
- **Rule 3 / rule 4.** The plugin declares the Better-Auth-owned **`subscription`** table + `stripeCustomerId` on `user` — emitted by `pnpm auth:generate` (register the plugin FIRST), migration **0019**. So the service is **read-only over `subscription`** (rule 4): all mutations go through the plugin's client/API (checkout, portal, webhooks), never a Drizzle write.
- **Trial is APP-MANAGED, not Stripe-managed.** A fresh school is fully usable for **`TRIAL_DAYS` (14)** from `organization.createdAt` — no card, no Stripe object. Stripe only enters at subscribe, which is why the plans carry **no Stripe `freeTrial`** (that would double-dip). This decouples "usable from minute one" from Stripe, matching the storage/mailer "unset → degrade" ethos — unset env → the whole app still runs on the trial and the pricing UI shows a "billing not configured" notice (never a broken subscribe button).
- **Entitlement is derived, not stored** — the single source of truth is the pure, unit-tested **`resolveEntitlement`** in `shared/billing.ts` (CORE, no Nuxt/Node — loads on client, server, and the `auth` CLI): given the org's subscription snapshot (null = never subscribed) + `orgCreatedAt`, it returns `{ status: 'trialing'|'active'|'past_due'|'canceled'|'none', entitled, planId, trialDaysLeft }`. **Fail-safe** (an unknown Stripe status never entitles — mirrors `consentState`), defensive against a missed webhook (an `active` row whose period already ended blocks), and a real subscription (even canceled) **never falls back to the trial**. `shared/billing.ts` also holds the `BILLING_PLANS` display catalog (names/features via i18n, prices display-only — Stripe is the billing truth; **price IDs are env, kept out of shared** so the client imports it cleanly).
- **Service — `server/utils/services/billing.ts`** (read-only): `getOrgEntitlement(orgId)` (the gate's question) + `getOrgBilling(orgId)` (entitlement + subscription summary for the page). Picks the **representative** row when an org has several (prefer a currently-entitled one, else most-recent). Every read scoped by `referenceId = organizationId` (tenant isolation, server-tested).
- **The gate.** `requireActiveMembership` gained a `{ allowUnentitled }` opt + a **method-based subscription check**: a lapsed school can still **READ** (the client routes it away) but a **mutating** request (`POST/PUT/PATCH/DELETE`) 402s with `SUBSCRIPTION_INACTIVE` — no operating a school you aren't paying for. GET/HEAD and Better-Auth-native subscription calls bypass, so the owner can always reach checkout/portal. Entitlement is surfaced to the client on **`AppContext.entitlement`** (active org only); `resolveAreaRedirect` + the `resolve-home` middleware route a non-entitled org to the terminal **`/billing-required`** page (uses the `auth` layout + only the `auth` middleware — no area guard, no loop; owner subscribes there, non-owners get "contact your owner" + school switch — mirrors `/access-paused`).
- **UI.** `GET /api/school/billing` (school roles; entitlement + subscription summary + `configured`) feeds `/school/billing` (in-area management: plan status, `Manage billing` → Stripe Customer Portal where cancel/card/invoices live, plan change) and `/billing-required` (the gate). Both render `components/billing/PlanPicker.vue` off `BILLING_PLANS`. Client actions live in **`useBilling()`** (`upgrade` → Checkout, `openPortal` → Portal; both redirect via `navigateTo(url, { external: true })`), gated to owner in the UI and re-checked by `authorizeReference` server-side. Client plugin: `stripeClient({ subscription: true })` in `auth-client.ts`. The former `soon()` Payments nav stub is replaced by a **Billing** link; the stale "Coming soon" tiles on `/school` (which mislabeled the finished Schedule) were removed.
- **Verification:** unit (`test/unit/billing.test.ts` — trial/entitlement/fail-safe/plan catalog) + server (`test/server/billing-service.test.ts` — trial, active/canceled, multi-row preference, tenant isolation, against Postgres; and the 402 gate cases in `require-active-membership.test.ts`). **Never touches Stripe** — server tests seed the `subscription` table directly (test-only write, like `expireInvitation`).
- **Not built (V1 follow-ups):** per-plan **feature/seat limits** (the catalog carries display `limits` but nothing is enforced yet), annual billing (a `annual` seam on `upgrade`), and a short **`past_due` grace window** before hard block. ## Lesson-fee payments (Stripe Connect)

The **other** money flow: **parents pay the school** for lessons (distinct from the school→Courtto subscription above). Here **the school is the merchant of record and Courtto is the platform** — so it's built on **Stripe Connect (Express)**, not the Better Auth Stripe plugin (which is subscription-only). **CORE, product-neutral plumbing:** the future Courtto marketplace collects court-booking fees through the *same* connected account, so nothing in the payment primitive references lessons; it moves with the core.

**Locked architecture (decided up front — do not re-litigate):**
- **Stripe Connect Express, DIRECT charges on the connected account** + `application_fee` for Courtto's cut. Direct charges mean customers/products/prices/subscriptions/**invoices all live on the school's account** — so the school is unambiguously the merchant (issues the *faktura*, Stripe Tax computes *their* VAT, they own disputes). Reuses the same `STRIPE_SECRET_KEY` (one platform account).
- **Pricing = a reusable plan catalog** (`pricingPlan` per school), a group (`lessonSeries`) references a plan — NOT a price-on-group. Recurring **monthly group subscriptions**.
- **Payer = the guardian**, paid via an emailed **hosted Checkout / Customer Portal link — no parent login** (reuses the guardian + email layers). Student self-pay in `/my` is a later additive channel.
- **Failed payment → `past_due` flag + notify; staff decides** (no auto-unenrol, no attendance block).
- **Collecting fees requires an active Courtto subscription** (consistent with the 402 mutation gate).
- **Commission** is `application_fee_percent` from `PLATFORM_FEE_PERCENT` (default **0** — wired, takes nothing until set).
- **Fiscal invoicing/VAT = Stripe Invoicing/Tax on the school's account** + export (full *faktura*/KSeF integration is a later, separate stream).

**Financial-integrity invariants (non-negotiable, every phase):** Stripe is the **source of truth** — app state is mirrored via **webhooks**, never computed locally · **idempotency keys** on every money call · money is **integer minor units (grosze)**, never float · immutable records + an **audit trail** of every movement · webhooks **signature-verified + idempotent** · **zero card data** touches us (hosted Checkout).

- **Config — `server/utils/payments-config.ts`** (CORE): the raw Stripe SDK client for Connect, env via `node:process`, module-level lazy singleton, **no factories/`useRuntimeConfig`** (rule 2), a **test seam** (`setPaymentsStripe`/`clearPaymentsStripe`, like the mailer's). `isPaymentsConfigured()` (unset `STRIPE_SECRET_KEY` → the UI degrades to a notice, never a broken button), `connectWebhookSecret()`, `platformFeePercent()`. Env: `STRIPE_CONNECT_WEBHOOK_SECRET`, `PLATFORM_FEE_PERCENT`.
- **Account readiness is derived, not stored** — the pure, unit-tested `resolvePaymentAccountStatus` / `canCollectPayments` in `shared/payments.ts`: `none` | `pending` | `ready`. `details_submitted` alone never reads as ready — Stripe can hold an account restricted while it verifies, so a school is only "ready" when **charges are enabled**. Fail-safe (anything short of `ready` blocks collection).

- **Phase 1 (done): Connect onboarding.** App-owned `orgPaymentAccount` (`app-schema.ts`, PK = org, migration **0020**) mirrors the connected-account flags; **Stripe is the source of truth**, kept fresh by the Connect webhook + an on-demand live sync on read. `services/payments.ts`: `startOnboarding` (idempotent get-or-create Express account — double-guarded by the DB row **and** a Stripe idempotency key — then a fresh AccountLink), `getPaymentAccount` (live-syncs the mirror on read), `syncAccountFromStripe`. REST: `POST /api/school/payments/connect` (**owner-only** — money is never an admin's to set up; a POST, so the subscription gate applies), `GET /api/school/payments/account` (school roles). **Connect webhook** `POST /api/webhooks/stripe-connect` — its OWN endpoint (separate from the subscription plugin's), **signature-verified**, handles `account.updated` (naturally idempotent → no event-id dedupe table until later phases carry money). Never 500s back to Stripe on a post-verification hiccup (would trigger retry storms) — captures + acks. UI: `/school/payments` (sidebar *Payments*, owner sets up, others see "contact owner") with none/pending/ready states. Verified: unit (`test/unit/payments.test.ts` — readiness derivation) + server (`test/server/payments-service.test.ts` — idempotent create, live-sync to ready, tenant isolation, against Postgres, via an injected fake Stripe — **never touches Stripe**).
- **Phase 2 (done): pricing-plan catalog.** App-owned `pricingPlan` (`app-schema.ts`, **ACADEMY** — it prices lessons; migration **0021**) — a reusable monthly plan a group will reference (P3). Each plan is mirrored as a Stripe **Product + recurring Price on the connected account** (direct charges), created/updated by `services/pricingPlans.ts`. `amountMinor` is **integer grosze**; `currency` is snapshotted from the school's profile at creation. A **Stripe Price is immutable**, so changing the amount creates a NEW price + deactivates the old (existing subscriptions keep it — the locked grandfathering policy); **archive** soft-deletes (deactivates the Stripe objects, keeps history — reversible). Plan creation requires a connected account (`PAYMENTS_ACCOUNT_REQUIRED`). - **Phase 3a (done): the billing spine** (backend + webhooks, fully tested against Postgres with an injected fake Stripe — **never touches Stripe**). A group (`lessonSeries.pricingPlanId`) references a plan; `services/enrollmentBilling.ts` turns a confirmed enrolment into a subscription-mode **Stripe Checkout** on the connected account (`createCheckoutForEnrollment`) and emails the payer the link (`renderPaymentLinkEmail`; the endpoint returns the URL too). **Payer:** a minor → their **primary guardian** (must have an email, else `PAYER_NO_GUARDIAN`); an adult student → themselves. **One Stripe Customer per payer**, reused (stored on `memberGuardian`/`memberProfile.stripeCustomerId`). The org named in the subscription's **metadata is treated as attacker-influenced, not a trusted claim**: we write it at checkout, but it rides on an object living on a connected account the *school* controls, so the sync **binds it to the account the event fired on** (`orgPaymentAccount.stripeAccountId` must match) — a school can only ever move its own enrolments' billing state, never another tenant's by naming them in metadata. A **double subscription** that slips through is cancelled and the first kept (never double-charge a family). Failed payment → **`past_due` flag only** (staff decides — the locked policy; access is never gated on payment). `application_fee_percent` is applied only when `PLATFORM_FEE_PERCENT > 0`. - **Phase 4a (done): staff cancel + refund.** `services/enrollmentBilling.ts` gained `cancelEnrollmentSubscription` (at period end by default — the humane school default — or `{immediately}`; then mirror the state) and `refundLatestPayment` (full refund of the subscription's latest invoice). **MONEY-OUT safety:** the refund's **idempotency key is the invoice id**, so a retry / double-click can never issue a second refund; validation (`bad(...)`) runs OUTSIDE the Stripe try/catch so it's never mis-reported as a Stripe 502; **refund is owner-only** (`POST /api/school/schedule/enrollments/[id]/refund`), cancel is school-role (`POST .../cancel`). - **Phase 4b (done): past_due notifications.** On the webhook TRANSITION into past_due (`syncEnrollmentSubscription` compares the stored status to the new one), `services/paymentNotifications.ts` `notifyPaymentFailed` alerts school STAFF (owner + admins) over the in-app bell (new `billing.payment_failed` type) + email (`renderPaymentFailedEmail`). The PAYER is deliberately NOT emailed from here — Stripe sends its own dunning + retries (the locked "flag + notify staff, staff decides" policy; access is never gated on payment). Best-effort + per-recipient isolated (a notification failure never fails the webhook), and the transition guard means a Stripe retry while already past_due doesn't re-fire. Verified: unit (type known + non-system) + server (one alert on the transition, none on a repeat past_due sync).
- **Phase 5 (done): money-audit ledger.** An append-only `paymentAudit` table (`app-schema.ts`, migration **0024**) records every staff MONEY MOVEMENT — `checkout_sent` / `subscription_canceled` / `refund_issued` (`shared/payment-audit.ts` action keys) — with the actor + subject **name-snapshotted and denormalized (no FK)** so an entry outlives the member/enrolment it names, `amountMinor` (integer grosze) + `currency` + the Stripe object id (`stripeRef`) for reconciliation against Stripe. `services/paymentAudit.ts`: `recordPaymentAudit` is **best-effort** (a failed trail write never fails the money op — Stripe stays the authoritative ledger) + `listPaymentAudit` (recent, org-scoped). The three staff operations take an optional `actor` and record their own complete entry; the endpoints pass it from the session (so production always audits, non-request callers can skip). UI: a **Payment activity** feed on `/school/payments`. Verified: unit (action keys) + server (an entry per checkout/cancel/refund with the actor + refund amount, tenant-scoped, skipped without an actor).
- **Phase 6 (done): billing stops when the spot ends — the lifecycle↔money link.** Until this, `cancelEnrollmentSubscription` was reachable ONLY from the explicit staff "Cancel billing" button: ending a spot any other way left the family being charged monthly forever. Four leaking paths (staff removing a spot, a student self-cancelling in `/my`, `cancelSeries`, `purgeSeries`), and it was **silent** — `listSeriesEnrollments` filters out `cancelled`, so the manual action disappeared from the panel the instant the spot ended, and `/school/payments` has no subscription list; a purge additionally cascaded `enrollment` → `enrollmentBilling` away, erasing the subscription id. Fix: `stopBillingForEnrollments` / `stopBillingForSeries` (`enrollmentBilling.ts`), emitted **from the mutation services post-commit** (`cancelEnrollment`, `cancelSeries`, `purgeSeries`) exactly like the lesson-notification pipe — so **every** call path stops the money and no handler has to remember. **Cancels AT PERIOD END** (the paid month is honoured, no further charge, never a surprise refund — the same humane default as the manual cancel), and **expires** a never-completed Checkout link so a stale email can't subscribe a payer to a dead spot. **Order is the safety property in `purgeSeries`: stop BEFORE the delete**, because the delete cascades the subscription id out of the database. Best-effort + per-enrolment isolated (a Stripe outage must never fail a cancellation) but **never silent** — failures are captured, and each stop writes a `subscription_canceled` money-audit entry whose **denormalized, FK-free columns outlive the purge**, leaving the subscription id for reconciliation as the only surviving record. Idempotent (a row already `canceled` or already `cancel_at_period_end` is skipped), so a double-cancel neither calls Stripe twice nor duplicates the trail. Verified: server (all four paths, the unpaid-link expiry, idempotency, Stripe-unreachable, tenant isolation, and that the trail survives a purge — **each lifecycle test confirmed to fail without the emit**).
- **The lesson-fee payments feature is complete (P1–P6).** Remaining (later, not built): passes / one-off charges, a **parent portal** (guardian login — gap #7), **KSeF** e-invoicing, and **revenue on the owner dashboard** (gap #8's money half). A **subscription roster** (every active subscription for a school, independent of the enrolment that created it) is the documented follow-up — the money-audit trail is today's answer to "what is still charging?", which is a trail, not a live list. Operational go-live: enable Stripe Connect on the platform account, set `STRIPE_CONNECT_WEBHOOK_SECRET`, register the Connect webhook at `/api/webhooks/stripe-connect`.

## Compliance report

`/school/compliance` (sidebar *Compliance*, school roles — PII) — the roster-level RODO/GDPR gap view (closed backlog gap #4). CORE, like the guardian + consent models it composes. The two gaps are deliberately **one shape, one report**: a student with a compliance gap, whatever the gap.

- **The two gaps** (`shared/compliance.ts` `evaluateCompliance`, pure + unit-tested): **missingGuardian** = `needsGuardian` (a minor with zero guardians), **missingImageConsent** = image `consentState === 'unknown'`. **The doctrine-critical line: a WITHDRAWN consent is NOT a gap.** Only `unknown` ("never asked") is chase-able; surfacing a withdrawal would nudge staff to re-ask a decision they must respect (see the consent doctrine). A unit test guards this. Both gaps compose the existing tested helpers (`isMinor`/`needsGuardian`, `consentState`) — no new domain math.
- **Population = the active student roster** (`role='student'`, coalesced status `active`). Staff are adults on an employment basis, so they're deliberately out of scope — the report is a work-queue, not noise. A null DOB can't establish minority, so it never raises the guardian gap (no false "needs guardian" on every DOB-less student).
- **Service — `services/compliance.ts`** (`getComplianceReport`, read-only): **set-based, O(1) queries** regardless of roster size — one join for students + profile + image consent (the `(memberId,type)` unique index keeps it 1:1), one grouped `COUNT` for guardians, merged in memory. Every query scoped by `organizationId` (tenant isolation, server-tested). Returns the gap subset (rows) + summary counts over the whole population (so tiles read "12 of 180"), ordered most-urgent-first (a minor with nobody to call leads).
- **UI — `app/pages/school/compliance.vue`:** summary tiles (clickable → filter), a gap-type filter + search, and a table where each row links to the member cockpit (its Overview tab holds the guardian + consent cards to fix). Celebratory all-clear empty state. `useLazyFetch` + `USkeleton`. The DTO has no Date fields, so it binds directly (no view-type mirror needed).
- **Not built (follow-ups):** a CSV export (the directory's `buildCsv` makes it trivially additive) and surfacing the gap count on the owner dashboard.

## Known gaps (V1 backlog)

Recorded honestly so nobody re-derives them, roughly ordered by what blocks a sale. Everything here is a **known** gap, not an oversight — if you close one, strike it.

1. ~~**No email provider — a forgotten password is a permanent lockout.**~~ **DONE — the mail layer ships (see "Transactional email" below).** Password reset is wired end-to-end (`sendResetPassword` + `/forgot-password`·`/reset-password` pages) and staff invitations are now emailed (additive; the copyable link stays as the bounce fallback). The *rest* of the email story (transactional lesson notifications) is gap #2, not this.
2. ~~**The notification pipe carries exactly one message.**~~ **DONE — the operational lesson pipe ships (see "Lesson events" under Notifications).** Cancel, reschedule, waitlist-promotion and a nightly-pattern ~24h reminder now reach the enrolled students, the coach, and a minor's guardian (by email) — in-app + email, best-effort, localized. Remaining follow-ups (not blockers): **whole-series cancellation** and **coach reminders** aren't wired (bounded out of the phase to control email volume), and per-user **channel preferences** (email opt-out) were deferred — the emit path is built pref-ready.
3. ~~**Payments are a `soon()` nav stub.**~~ **DONE — SaaS subscription billing ships (see "Billing & subscriptions").** The school pays Courtto via the Better Auth Stripe plugin: 14-day app-managed trial → Checkout → Customer Portal, org-scoped subscriptions, a derived entitlement that gates mutations (402) + routes a lapsed school to `/billing-required`. 4. ~~**No roster-level compliance-gap view.**~~ **DONE — the compliance report ships (see "Compliance report").** One view at `/school/compliance` surfaces the two same-shape gaps (a minor with no guardian; a student never asked for image consent), each row linking to the member cockpit to fix. Withdrawn consent is deliberately **not** a gap (a respected decision, not chase-able paperwork).
5. **`coach` and `student` have identical permission statements** (both `memberAc` in `shared/permissions.ts`). They differ only by area routing, not by capability — the permission matrix is unbuilt. Fine while areas are the only boundary; a real gap the moment one role needs a capability the other lacks.
6. **A guardian's consent is never re-confirmed when the member turns 18.** Consent given by a parent at 15 still reads `granted` at 18. Legally murky and deliberately unmodelled; `calculateAge`/`isMinor` already give the signal if this needs an expiry/re-ask flow.
7. **Guardians can't sign in** — `memberGuardian` is a contact record with no `user` link, so there is no parent portal. Additive when wanted (a nullable FK), deliberately not carried as an unused seam.
8. **Partial org-wide roll-up.** The **owner dashboard** now ships (see "Owner dashboard"): headcount KPIs, today's timetable, facility-wide weekly occupancy heatmap, attention items, recent activity. Still missing: **revenue** (needs lesson-fee billing) and **trend-over-time** (headcount/occupancy deltas) — the dashboard is a point-in-time snapshot, not a time series yet.
9. **The 3-surface plan is only 2/3 built.** `Members/Access` (core) exists; Academy **Students** and **Coaches** list surfaces don't — the directory segments Staff/Students instead, which covers V1. Revisit when the Academy people-analytics need their own home.
10. **No e2e coverage for the members surfaces.** Directory / cockpit / guardians / consents are covered by unit + live-Postgres server tests; Playwright still only drives signup, role routing, permission denial and the cache-isolation regression.
11. **Nothing has a retention policy.** `auditLog` and `paymentAudit` are append-only forever by design, and `notification` + `attendance` only grow; a school will eventually want archival/pruning, and RODO wants a stated period, not just a clause in a policy document. Needs a decision per table plus a scheduled sweep (the nightly-task pattern already exists). **A proposed table — period + legal justification per record type — now exists in `docs/legal/README.md`** and needs approving, then implementing; until it does, the published privacy policy deliberately states current behaviour rather than the target, so the two don't contradict each other. Note the accounting collision the proposal calls out: art. 74 uor (5 years) beats art. 17 erasure, so payment records must be **anonymized, not deleted** — `paymentAudit`'s FK-free columns already allow it.
12. **No school-side (controller) export or erasure of a student's record.** `/account` covers the *account holder's own* data (see "Account & self-service data rights"), which is the half Courtto holds as controller. The other half — a parent asking the school to hand over or delete everything it keeps about their child — has no surface: `archived` retains the row by design, and a hard delete would cascade through enrolments and attendance into records the school must keep for accounting (art. 74 uor, 5 years). Needs a product decision on what is erased vs **anonymized**, then a staff-facing flow on the member cockpit.

## Known gotchas

- **Nuxt UI v4 renamed `UButtonGroup` → `UFieldGroup`** (groups buttons + inputs). The old name fails silently at runtime.
- `node:` builtins need `@types/node` (installed) to typecheck.
- **Don't hand-write a row-value keyset tuple** (``sql`(created_at, id) < (${date}, ${id})` ``): postgres-js mis-serializes a bare `Date` against a plain `timestamp` column (`ERR_INVALID_ARG_TYPE`). Use typed drizzle operators instead — `or(lt(createdAt), and(eq(createdAt), lt(id)))` — so the driver knows the column type. `typecheck` and `lint` both pass this bug; only a run against a real Postgres catches it.
- **Verify against a real database before claiming done.** Static gates don't catch driver, constraint or migration bugs. Disposable Postgres: `docker run -d -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=courtto_test -p 5433:5432 postgres:16`, then run `pnpm test:server` with `TEST_DATABASE_URL` + `BETTER_AUTH_SECRET` set. **Use a low port** — on this Windows host Hyper-V reserves the 55xxx range and `-p 55432:5432` fails with a socket-permission error.
